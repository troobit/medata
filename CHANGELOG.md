## [Unreleased]

### Fixed

- **Glucose widget sat a reading behind whenever a CGM row was timestamped ahead of the device clock** (`App/GlucoseWidgetPublisher.swift`): `currentSnapshot` queried the closed window `[now − 24 h, now]`, so any `bsl` row stamped even a second into the future was excluded from the read entirely and the snapshot kept the previous reading for as long as the skew lasted. The bug is invisible from the render side, because `GlucoseTimeline.render` already handles exactly this case — it clamps a future reading's age to zero on the stated grounds that "a reading timestamped in the future is clock skew, not a prediction" (Req 5.5) — but with the query's upper bound at `now` that clamp was unreachable: the row never got as far as the snapshot. The asymmetry is what made it hard to see from the app, since the Trends screen queries to the end of the calendar day and so displayed the same row perfectly well. The upper bound is now `now + futureSkewAllowance`, one hour. Bounded rather than open-ended deliberately: a future reading clamps to age zero and therefore renders as *fresh*, so an unbounded window would let a single corrupt far-future row pin the widget to a wrong value indefinitely — an hour absorbs real clock and timezone-rounding skew while capping that blast radius. `TrendsMath.glucoseRate` still filters `timestamp <= now` and so excludes a future reading from the least-squares fit; that is left as-is, since it anchors trend and staleness to the same clock by design, and the effect under skew is a conservative arrow (or none) beside a correct value rather than a wrong one. Also adds the publisher's first diagnostics, all `subsystem == "ie.medata.app"` so `make logs-device` picks them up with its existing predicate and `--info --debug`: `publish.reloadRequested` (with the previous and new reading stamps, the trigger, and lag) and `publish.skipped` at debug level for the unchanged recompute that is the common case for an insulin or intake tick. Every interpolation is `privacy: .public` — `os_log` redacts non-literals by default and would render the timestamps as `<private>`, which is precisely the information these lines exist to carry. `publish.futureReading` logs the observed skew so the field diagnosis can be confirmed or refuted on the next device pass, and `publisher.streamEnded` is an `error`-level line after the `for await` loop, reachable only if the store's broadcaster finishes the stream — a state in which the widget has silently stopped updating for the rest of the process lifetime and which previously produced no signal at all.

- **Accuracy harness reported a passing bar for fixtures carrying no ground truth** (`HarnessCore/AccuracyHarness.swift`, `HarnessCLI/main.swift`, `Makefile`, `MedataCore/Tests/HarnessCLITests/AccuracyHarnessTests.swift`, `specs/bugfixes/accuracy-harness-scores-untruthed-fixtures-as-zero/`): `HarnessCLI accuracy` scored untruthed meals as *perfect* — `pointMAPE` guards `act > 0 else { return 0 }`, contributing 0 % error per meal, and `pointMAE` has no guard at all and averages `|predicted − 0|`, i.e. the prediction itself. Since `CaptureBundleRecorder` deliberately leaves `ground_truth_*` at proto3 defaults (weighed truth is back-filled off-device), **every** bundle pulled off the phone has zero truth, so a field replay returned `mape: 0`, `mae` = the predicted grams, and — for any prediction ≤ 25 g — `passesBar: true` with exit 0. Not a wrong number but a confident pass on a measurement that never happened, in the one instrument meant to answer "did this checkpoint improve accuracy?". The fix is applied in `evaluate(meals:)` rather than in the metric helpers, because `perClassStats` *depends* on that `return 0`: it calls both helpers against a synthetic `Array(repeating: 0, ...)` since per-class truth is absent from `MealEvalInput`, so changing the helpers would have silently altered the per-class block (Decision 1). `evaluate` now partitions on `isScorable(truth) = truth.isFinite && truth > 0` — covering negative, NaN and infinite truth as well as proto3 zero — feeds only scored meals to MAPE/MAE and counts scored meals for the `n ≥ 30` bootstrap-CI threshold, and `passesBar` gains a `scoredCount > 0` conjunct, since even correct metrics over zero scored meals yield 0/0 and satisfy `mape < 20 && mae <= 25`; an empty run now fails rather than passes. `AccuracyReport` gains `scoredCount`, `unscoredCount` and `rows: [MealErrorRow]`, the latter carrying per-fixture id, capture path, truth, prediction, `absoluteErrorG` and `percentError` — the two error fields **optional and null when unscored** rather than zero, because zero reads as an exact prediction and `|pred − 0|` reads as a large but genuine error, while `null` cannot be mistaken for a result or silently averaged (Decision 2); the prediction stays on the row, since what the model *said* is the main reason to replay an untruthed field bundle. `perClassStats` and `latencyStats` still run over all meals — they describe distribution, calibration status and timing, not error. CLI side: `runAccuracy` and `runLegacyEval` carried byte-identical emit-and-exit blocks and now share one `emitAccuracy` helper; `AccuracyJSON` gains `scoredCount`/`unscoredCount`/`rows` plus `checkpointSHAs`, the distinct segmenter stamps across loaded fixtures, so a run that mixed models is visible rather than silently aggregated; any untruthed meal prints a stderr warning naming the count and pointing at off-device back-fill, and a run that scored nothing exits 1 with `FAIL: no meal carried ground truth`. New `make harness-accuracy` target (`FIXTURES=`/`SHA=`/optional `OUT=`) — the harness previously had no Make entry point at all despite the convention that tooling runs through `make` — whose help states up front that untruthed bundles report UNSCORED and exit non-zero, so that is not read as a defect in the captures. A planned fifth change was **dropped on inspection**: relaxing `FixtureLoader`'s `--checkpoint-sha256` equality was premised on the operator not knowing the fixtures' stamp, but `Error.checkpointMismatch` already carries `got:` and the CLI prints it, so the friction is one extra run — not worth trading a guard that stops a run silently mixing checkpoints. Five new tests (XCTest 510 → 515 executed, 5 skipped, 0 failures; swift-testing 203 in 25 suites unchanged) pin the all-untruthed run failing the bar with nil error fields, untruthed meals not moving the aggregates (proven with a deliberately wild 500 g untruthed prediction alongside two truthed meals), scored rows carrying per-fixture error, the empty run failing, and non-positive/non-finite truth being unscorable. Developer tooling only — `HARNESS_ENABLED` keeps all of it out of the shipping iOS binary. Two adjacent defects found and deliberately left: `perClassStats` reports `mape: 0` and `mae` = mean predicted grams for every class by construction, and `runAccuracy` still builds `ClassPalette.v1Standard` while the promoted bundled model is 36-channel palette v2. Not verified end-to-end — no `.fixture` exists in the repo, so the replay against a real bundle remains `capture-bundle-recorder` task 4 in the P0 device session.

Two findings drove the ordering. P1–P3 then close the capture → truth → error loop, which is half-built: `CaptureBundleRecorder` already writes a fully replayable `PbMealFixture` per attempt in Release, the proto already carries `ground_truth_*`, and `AccuracyHarness` already computes MAPE/MAE/bootstrap CIs, but nothing joins them. The loop is currently not merely incomplete but actively misleading — `AccuracyHarness.pointMAPE` guards `act > 0 else { return 0 }` and `pointMAE` averages against zero, so replaying a device bundle (truth zero by design) reports MAPE 0 % and MAE equal to the predicted grams, a confidently wrong pass; that is filed as a `specs/bugfixes/` correctness defect rather than an enhancement. The design decision recorded is to reuse the existing in-app benchmark surface (`BenchmarkMeal`/`BenchmarkFidelity`/`BenchmarkView`/`BenchmarkReport`, already producing per-meal `absoluteErrorG` against `BenchmarkAnchors`) as the truth source rather than building a second one, to join truth by a `--truth-manifest` CSV at evaluation time rather than mutating recorded `.fixture` files, and explicitly *not* to repurpose `PbUserCorrection` (it means "adjusting the portion", carries no fidelity flag, hangs off `MealRecord` not the attempt, and would silently mix corrections with measurements). Three replay-fidelity defects are documented as making any replayed figure not the device's figure: `FixtureRunner.run` routes every `single_dominant` fixture — which all device bundles are — to the centre-seeded `fitPlateRegionPlane` written for the Nutrition5k overhead rig, so handheld captures skip; β is pinned to 1.0 on replay so the calibrated shipped chain is never measured; and bundles always claim `single_dominant` even with oblique data present, so two-view captures can never replay on the `twoViewSfS` branch. The pivotal open trade is called out for a decision-log entry: the full-resolution probability tensor is what makes replay exact, but it costs ~200 MB per capture *and* freezes the segmentation, so a new checkpoint can never be evaluated against an old capture — the promote-to-corpus step (keep PNG/depth/intrinsics/gravity/truth, drop probs, re-segment on replay) is what turns the recorder into a durable regression corpus. Per PROCESS §3 none of this needs a new spec: the tooling extends `capture/capture-bundle-recorder` (which deferred truth back-fill in its own out-of-scope list rather than ruling it out, and should grow from smolspec to full spec in place), the bar it measures against already lives in `estimation/model-production`, and `estimation/estimation-quality` is explicitly *not* the home despite the name — its PRD scopes training recipe, mask post-processing and variance reduction, and non-goals data collection. Also records four spec-hygiene drifts: `OVERVIEW.md` reports `segmenter-foundation` at 19/22 against a ledger at 18/22 since `bc4b060`, `ui/mass-readout` shipped code at `0c6a6b6` with no `tasks.md` (failing the PROCESS §11 checklist), `bugfixes/two-view-carve-no-volume` is mis-filed as a carve defect when the root cause is capture-side, and `nextup.md` still points only at glucose-lock-widget task 14. `docs/README.md` gains the index row and its "Current state" line is corrected — it described the segmenter slot as holding the development stub, which is now true only of Debug.

### Added

- **Glucose Lock Screen widget — spec authored** (`specs/ui/glucose-lock-widget/`, docs only, no code): full spec for a WidgetKit accessory widget that surfaces the current/most-recent `bsl` reading and a derived trend arrow on the Lock Screen and StandBy with a glance. A matte surface returns a weaker LiDAR signal dominated by **MEDIUM (127 = 0.498)**, so every candidate point was filtered out → `noLidarPoints` → "no flat surface". Fixed by lowering `τ_conf` to `0.40` (Decision 49): MEDIUM-or-better is now accepted and only genuine LOW/zero returns are dropped; the RANSAC 5 mm inlier band + 20 mm residual gate still reject a bad plane and `σ_plane` carries the extra noise (consistent with Decision 46).
